`react-3d-mockups` renders procedurally generated 3D devices with WebGL and maps
real, live DOM onto their screens: text stays vector crisp at any angle,
videos play, iframes load, and React state and effects keep running. There are
no 3D asset files to host and nothing to download at runtime.

<Callout type="warn" title="In active development">
  The API may change over the next few weeks. Breaking changes are listed in the
  [changelog](https://github.com/area-is/react-3d-mockups/blob/main/CHANGELOG.md) with
  what to change; pin an exact version
  (`npm install --save-exact react-3d-mockups`) if you need it to stay put.
</Callout>

## Highlights

- **Thirty-three devices and twenty-five objects**: phones, foldables,
  tablets, laptops, watches and a monitor, plus print, packaging, out-of-home
  formats, vehicles, a TV and custom-size panels and boxes. The screen or
  printable surface of each is a live DOM area. Browse them all in the
  [gallery](/docs/gallery).
- **True-to-device screens**: each virtual display defaults to the real device's
  logical resolution in portrait and landscape, so your layouts and breakpoints
  behave exactly like on the hardware.
- **Real GPU rendering**: three.js and react-three-fiber, physically based
  materials, studio lighting, soft shadows, clamped device pixel ratio.
- **Any content on screen**: pass React components, an `<iframe>`, or a
  `<video>` as children. State, effects, and media playback keep running, and
  text stays vector crisp at every angle. Screens are decorative - every
  gesture belongs to the orbit controls, so pointer events never reach the
  content. See [Screen content](/docs/screen-content).
- **Composable**: use the one-liner mockup components, or drop the bare devices
  into your own react-three-fiber scene.

## What it is not

- **Not an interactive device.** Screens are display-only: your content
  renders live, but clicks, taps, scrolling and typing go to the orbit
  controls and never reach it. Put a usable app next to the mockup, not on
  it. [Why screens are display-only](/docs/screen-content#why-screens-are-display-only)
  explains the trade.
- **Not an official product model.** The devices are original procedural
  approximations built from published specifications and product
  photography - close enough for design work, not dimensionally exact, and
  not affiliated with their manufacturers. See
  [Trademarks and usage](/docs/trademarks).
- **Not a server-side renderer.** WebGL exists only in the browser, so the 3D
  picture is drawn there; server rendering outputs only the mockup's empty
  wrapper. See [Next.js and SSR](/docs/nextjs) and
  [Other frameworks](/docs/frameworks).
- **Not an image exporter.** A canvas snapshot misses the screens, because the
  browser composites them. [Exporting images and video](/docs/exporting) shows
  what works.

## Installation

```bash
npm install react-3d-mockups three @react-three/fiber @react-three/drei
```

React 19 is required (`^19.0.0`). React 18 is not supported: react-three-fiber 9
and drei 10, which the library is built against, both require React 19
themselves.

The supported `three` range is `>=0.179.0 <0.187.0`, the releases the library
has been tested against. If npm refuses the install because a newer three.js
has become `latest`, install `three@0.186` instead - see
[Troubleshooting](/docs/troubleshooting#unsupported-threejs-version).

`three`, `@react-three/fiber`, and `@react-three/drei` are **peer** dependencies
rather than bundled ones, because each has to exist exactly once in an app. Two
copies of `three` on a page mean two different `THREE.Mesh` classes, so
`instanceof` checks and react-three-fiber's element catalogue stop matching; two
copies of `@react-three/fiber` mean `useThree()` inside your own components reads
a different store than the one the mockup rendered into. Keeping them as peers
lets your app own those versions instead of this package pinning them.

You do not have to install them by hand: npm 7+ and pnpm 8+ resolve peer
dependencies automatically, so `npm install react-3d-mockups` on its own already
pulls all three in. Naming them explicitly is still worth it - it records them in
your `package.json`, so upgrades are yours to control and `import * as THREE from
'three'` in your own code resolves to a dependency you declared. Yarn (Classic and
Berry) does not auto-install peers, so there the full command is required.
