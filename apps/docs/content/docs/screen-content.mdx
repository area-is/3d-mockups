Anything the browser can render can live on a device screen. The screen is a
real DOM layer composited in 3D by CSS transforms, not a texture, so text stays
vector crisp at every angle — React components keep their state and effects,
`<video>` keeps playing, and an `<iframe>` keeps loading. Screens are
display-only by default; see [Interaction](#interaction) to make one clickable
and what that costs.

```tsx
// React components: state, effects, and events all keep working
<GalaxyMockup>
  <SignupForm />
</GalaxyMockup>

// A whole page via iframe
<GalaxyMockup>
  <iframe src="https://example.com" style={{ width: '100%', height: '100%', border: 0 }} />
</GalaxyMockup>

// Video, images, anything the browser can render
<GalaxyMockup>
  <video src="/demo.mp4" autoPlay muted loop style={{ width: '100%', height: '100%', objectFit: 'cover' }} />
</GalaxyMockup>
```

## The virtual display

Your content renders into a viewport that defaults to the device's logical
resolution, for example 360×780 CSS px on the Galaxy S26 and 1032×1376 on the
13" iPad Pro. Media queries, breakpoints, and `vh`/`vw` units inside the screen
behave exactly like on the real device. Pass `resolution` (the CSS pixel width
of the display) to override it; height always follows the panel's aspect ratio,
so the graphic stays true to the panel.

The full table of defaults per device is in
[Devices and resolutions](/docs/devices).

## Interaction

Every device accepts the same screen behavior props:

| Prop | Type | Default | Description |
| --- | --- | --- | --- |
| `interactive` | `boolean` | `false` | Let pointer events (clicks, scrolling, typing) reach the screen content. **Also changes how the mockup looks — read the warning below.** |
| `dragToRotate` | `boolean` | `true` | Drags that start on the screen spin the device after about 10 px of travel; taps still click. Disable when your content needs its own drag gestures (sliders, drawing, horizontal swipes). |
| `surfaceBackground` | `string` | `'#000000'` | CSS background painted behind your content, under whatever you render. See [Surface background](#surface-background). |
| `surfaceStyle` | `CSSProperties` | - | Extra styles merged onto the screen wrapper (for example a custom `fontFamily`). |

<Callout type="warn" title="interactive costs you visual accuracy">

Turning `interactive` on is not free, and it is not just a pointer-events
switch. A screen is real DOM composited into a WebGL scene, and where that DOM
has to sit in the stacking order decides how it can be hidden behind hardware.
There are exactly two options and you get one or the other:

**`interactive={false}` (default) — per-pixel blending.** The DOM stacks
*under* the canvas and is masked by the depth buffer, so anything in front of
the screen covers it exactly, pixel for pixel: a laptop's keyboard hides the
screen's reflection, a phone's proud camera ring stands over a wrap, a bus's
mirrors draw over the livery. Being under the canvas is also precisely why the
content cannot be clicked.

**`interactive={true}` — raycast occlusion.** The DOM stacks *on top of* the
canvas so pointers can reach it — which means nothing in the scene can visually
cover it. Hiding becomes all-or-nothing: sample rays decide whether the screen
is behind the body, and the whole screen blinks off together. Partial coverage
goes wrong in both directions — content shows through hardware that should hide
it (you can see a laptop's screen through its own keyboard), and a screen that
is mostly visible can blank out entirely.

Turn it on only when the content genuinely has to be *used* — a live embedded
app, a scrollable prototype, a form someone will type into. For screenshots,
hero images, landing pages and anything you'll export as a still, leave it off.

</Callout>

Both modes are per-region, so a mockup with several surfaces can mix them —
set `interactive` on the one slot that needs it and leave the rest display-only:

```tsx
<LaptopMockup>
  <LaptopMockup.Screen interactive>
    <YourLiveApp />
  </LaptopMockup.Screen>
</LaptopMockup>
```

A few surfaces are per-pixel no matter what you pass, because raycasting simply
cannot describe what covers them: the full-coverage wrap sides on `<VanMockup>`
and `<BusMockup>`, the glass on `<BusShelterMockup>`, and the outer cover of
`<FoldMockup>` / `<FlipMockup>`. Those never become clickable.

## Surface background

`surfaceBackground` paints *underneath* your content — black on lit screens,
white on print surfaces. It only shows where your content does **not** paint:
a logo on a transparent PNG, a layout shorter than the surface, rounded corners
on a card, the moment before an `<iframe>` finishes loading.

Pass full-bleed opaque artwork and you will never see it. That is why nudging
it in these demos looks like it does nothing — every demo here ships art that
covers the whole surface.

Do **not** set it to `transparent` hoping the hardware shows through. A
screen's DOM sits under the canvas (see the warning above), so transparent
pixels fall through to the page behind the mockup, and the screen reads as a
hole cut in the device. If you want the glass to look off, use a dark color.

```tsx
{/* a logo centered on brand color, not stretched to the corners */}
<IPadMockup surfaceBackground="#1d4ed8">
  <YourLogo />
</IPadMockup>
```

## Touch behavior

On touch devices the mockup never traps page scrolling: vertical swipes over
the canvas or the screen scroll the page natively, horizontal drags rotate the
device, and taps click your content.
